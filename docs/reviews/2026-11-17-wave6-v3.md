# Wave 6 V3 built production baseline

Base: `9e5a0fb`. Branch: `t3/wave6-v3`. Synthetic loopback data only.
Marketing impact: none.

## Profile and method

Node 22.23.2, pnpm 11.13.1, Next 15.5.29, Playwright 1.61.1 and Chromium
149.0.7827.55 on Linux, AMD Ryzen 5 6600H, 12 logical CPUs, 31,775,150,080
bytes host RAM. The installed forge-job wrapper caps the entire job at four
CPU equivalents and 6 GiB RAM. It does not support `--memory`. Builds and
measurements run sequentially, without another V3 test job running.

The production helper uses canonical UAT seeding, real Better Auth database
sessions, the existing persona GET gateway, snapshot/reset and cleanup. The
app runs `next start` with `NODE_ENV=production`, HTTPS configured for Better
Auth, optional Developer MCP disabled, and no dev DNS/fetch preload or E2E
configuration in the app process. Identity form POST and sign-out are not
proved. The existing loopback HTTP gateway has no reviewed TLS/trust setup.

Desktop readiness uses 1440x900, DPR 1, no browser CPU/network throttling.
Each route is primed once, then sampled 20 times by full document navigation.
Readiness includes a visible expected h1, an enabled primary control and two
animation frames; Assessment also waits for its hydrated backup control.
Nearest-rank p95 is sample 19 of 20. Cold navigation uses five fresh Next and
worker starts **per route**, a restored database and a fresh browser context
with the seeded session/storage. The startup probe fetches only a static SVG.
Cold figures exclude provisioning and server startup time, and include the
first application navigation after startup.

Mobile lab runs five samples per route at 390x844, DPR 1, 4x CPU slowdown,
150 ms network latency, 1.6 Mbps download and 750 Kbps upload, with browser
cache cleared before navigation. LCP is captured before scripted input.
CLS uses the maximum session window with gaps below one second, bounded to
five seconds, excluding recent input. Scripts open and close the navigation
menu by keyboard and type into editable route controls. Maximum Event Timing
duration includes processing and presentation, rounded by Chromium; values
below the 16 ms observer threshold are reported as at most 16 ms. These are
lab measurements, not field p75 INP.

Payload sums level-9 gzip bytes of the actual initial JS resource graph one
second after readiness, including initially fetched chunks. It excludes HTML,
inline RSC data and later PDF/export chunks. RSS samples every 250 ms and sums
process RSS, including shared pages in each process. Application RSS includes
the fixture controller, Next and worker; total RSS also includes Playwright
and Chromium. Docker database/Mailpit process memory is outside these process
trees. Three identical warmed route batches check retained application growth.

## First attempts and findings

The stock `tooling/uat/serve.mjs --start --build` completed the optimized
build, but its unconditional `DEVELOPER_MCP_ENABLED=true` caused production
configuration to reject requests with the OWNER-DEVELOPER-MCP-02 approval
error. All six proof cases failed. No route timings from this run constitute
a production baseline or a performance failure.

The owned production stack fixes fixture composition by leaving that optional
feature off and removing dev-only app configuration. A partial warm run then
exposed the collector's unbounded `networkidle` wait on Assessment. That run
was stopped and retained locally. The collector now uses a fixed one-second
initial-resource observation window and bounded browser actions/navigation.

The shell payload miss is shared. The build manifest assigns the same layout
chunks to all routes. Chunk 4657 is 153,382 bytes gzip and contains Radix UI
code; chunk 927 is 41,162 bytes gzip and contains Clerk client code even with
Better Auth selected. Chunks 5315 and 4295 add 21,736 and 17,975 bytes gzip.
The root layout statically imports ClerkProvider; the shell imports the broad
design-system entry. This is bundle evidence, not a measured query bottleneck.
Changing those unowned imports/configuration is an integration follow-up.

Layout-shift attribution shows the Assessment content changing from a
22.5-pixel loading status at y=306.97 to a 629-pixel viewport region at y=215
on mobile. Its footer leaves the viewport. The largest shift contributes
0.745261. The full Assessment becomes LCP at 3.5 to 3.668 seconds under the lab
profile. `modules/assessment/src/assessment-shell.tsx:101` returns a small
loading placeholder until hydration, then replaces it with the full UI.
This explains the measured CLS and delayed LCP. Reserving the final layout
and rendering useful initial content needs the S5 owner; no unowned product
code was changed. The shared shell payload cause is described above.

These gates prevent regression while the misses remain open. Passing them
does not mean Assessment meets the proposed LCP/CLS targets or UAT-015 is closed.
The final profile confirms Assessment TTFB is 29.8 to 57.6 ms, while its last
initial script completes at 3.223 to 3.251 seconds. The full view becomes LCP
at up to 3.612 seconds. This supports a client-loading/hydration cause rather
than a slow initial server response.
